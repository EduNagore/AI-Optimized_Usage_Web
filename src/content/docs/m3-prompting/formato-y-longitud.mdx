<KeyTakeaways>

- Enseña la forma con un ejemplo breve: describirla con palabras funciona peor.
- Para una persona, pide el formato según el uso («tabla solo para comparar»); para un programa, usa structured outputs.
- En vez de un límite de palabras, di quién lo lee y para qué.
- Si el modelo formatea de más, pide prosa; si formatea de menos, muestra la estructura que quieres.

</KeyTakeaways>

## La idea

El formato de la respuesta cuenta tanto como el contenido: un resumen en una pared de texto no se lee, y una tabla de una sola fila sobra. Hay dos situaciones distintas, y se resuelven de forma distinta.

**Cuando el lector es una persona**, la forma se pide con una descripción corta y, mejor, con un ejemplo de lo que quieres. El modelo imita lo que ve, así que un ejemplo transmite longitud, tono y estructura de una vez.

**Cuando el lector es un programa**, no basta con pedir «responde solo en JSON». Para eso están los structured outputs: se entrega a la API un esquema y la respuesta lo cumple. En la API de Anthropic, el esquema va en `output_config.format` con `type: "json_schema"`.

<Callout tipo="verificado" fecha="2026-10-16">

Los structured outputs están disponibles de forma general (salieron de beta) y se configuran con `output_config.format`, con `type: "json_schema"`. Sustituyen al antiguo parámetro `output_format`.

</Callout>

<Callout tipo="verificado" fecha="2026-10-16">

En Claude Opus 4.6 y posteriores, incluido Opus 5.5, terminar `messages` con una respuesta del asistente prellenada devuelve un error 400. Para fijar la forma, usa structured outputs o instrucciones en el prompt de sistema (en Amazon Bedrock, Opus 5.5 no admite structured outputs).

</Callout>

<Callout tipo="recomendacion">

Para cualquier salida que consuma un programa (una tabla de datos, una clasificación), usa un esquema y no una petición en texto. El porqué: el esquema garantiza la forma, y así dedicas tu atención a comprobar el contenido, no a reparar JSON roto.

</Callout>

## En la práctica

Tres técnicas para personas.

**Un ejemplo de forma.** «Responde así: _Decisión: …; Motivo: …; Riesgo: …_» consigue más que «sé conciso y estructurado».

**Formato condicional.** Dile cuándo usar cada formato: «usa una tabla solo para comparar opciones; en el resto, párrafos cortos». Evita las listas con viñetas para explicar razonamientos: la prosa conecta las ideas con su porqué.

**Público y propósito, no palabras.** «Máximo 150 palabras» se cumple a costa del contenido. «Para un directivo que lo lee en el móvil entre dos reuniones y tiene que decidir sí o no» da el mismo control con mejor resultado.

Si no obtienes lo que buscas, ajusta según el modelo:

## Ejemplo: un resumen de reunión que se lee

<BeforeAfter
  antes="Resume la reunión en menos de 100 palabras."
  despues="Resume la reunión para la directora, que no asistió y lo leerá en el móvil antes de otra reunión. Necesita saber qué se decidió y qué se espera de ella. Formato: «Decidido:» con una frase por decisión; «Te toca:» con lo que se le pide y para cuándo. Si no se pide nada, escribe «Nada por tu parte»."
>

Qué cambió y por qué: el límite de palabras se cambia por quién lee, dónde y para qué; y el ejemplo de formato («Decidido» y «Te toca») fija la estructura sin describirla. La frase final cubre el caso en que no hay nada que pedir, para que el modelo no invente una tarea.

</BeforeAfter>

## Errores frecuentes

- **«Responde solo con JSON» y analizarlo con un script frágil.** Se rompe el día que el modelo añade una frase. Usa structured outputs.
- **Depender del prellenado de la respuesta.** En los modelos Opus recientes devuelve un error 400: usa un esquema.
- **Pedir tablas para todo.** Una tabla ayuda a comparar; para razonar, la prosa es más clara.
- **Corregir el formato en cada turno.** Dilo una vez en el encargo, con un ejemplo.
